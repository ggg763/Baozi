# 通信协议（三套）

三端之间有**三条物理链路**，用**三套互不相同的协议**。
本文给出每一套的完整字段定义，与代码一一对应，可直接对着改。

| 链路 | 两端 | 代码位置 |
|---|---|---|
| ① | PC ↔ ESP32 | `pc_baozi/protocol.py` ↔ `esp32_baozi/protocol.h` |
| ② | ESP32 → TD1601 | `esp32_baozi/esp32_baozi.ino` ↔ `TD1601 src/uart_esp.c` |
| ③ | PC ↔ TD1601 | `pc_baozi/app/board.py` ↔ `TD1601 src/uart_protocol.c` |

---

## 链路 ①：PC ↔ ESP32（二进制帧）

**介质**：USB CDC（默认）或 WiFi/TCP 8765（`config.json` 的 `transport` 切换）。

### 帧结构（全部小端）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `0xA5` | magic0 |
| 1 | 1 | `0x5A` | magic1 |
| 2 | 1 | type | 见下表 |
| 3 | 1 | flags | 保留，填 0 |
| 4 | 2 | seq | uint16，递增回绕 |
| 6 | 2 | payload_len | uint16，**≤ 2048** |
| 8 | N | payload | |

`payload_len > 2048` 视为流错位，逐字节重新同步。
串口是字节流，两端都用「累积缓冲 + 状态机切帧」：

- Python：`protocol.py` 的 `FrameDecoder.feed()`
- C++：`link.cpp` 的 `feed()`

### type

| 值 | 名称 | 方向 | 含义 |
|---|---|---|---|
| `0x01` | MIC_PCM | ESP32 → PC | 麦克风 PCM，16 kHz / 16 bit / 单声道 / 小端 |
| `0x02` | TTS_PCM | PC → ESP32 | 待播放 PCM，同上格式 |
| `0x03` | CTRL | 双向 | 控制/事件，`payload[0]` 是控制码 |
| `0x04` | TEXT | PC → ESP32 | 调试文本（UTF-8，不保证 `\0` 结尾） |
| `0x05` | LOG | ESP32 → PC | 日志文本，PC 按行打 `[esp]` 前缀 |
| `0x06` | CAM_JPEG | ESP32 → PC | 摄像头 JPEG 分片 |

> 日志为什么走帧而不是直接写串口：这根线现在同时承载二进制协议帧，
> 裸文本会把帧流冲乱、两端都解析不了。

### CTRL 控制码（`payload[0]`）

| 值 | 名称 | 方向 | payload[1..] |
|---|---|---|---|
| `0x01` | PLAY_BEGIN | PC → ESP32 | — |
| `0x02` | PLAY_END | PC → ESP32 | — |
| `0x03` | PLAY_ABORT | PC → ESP32 | 立刻停止播放并清空缓冲 |
| `0x04` | PING | 双向 | 保活 |
| `0x05` | PONG | 双向 | 保活应答 |
| `0x06` | HELLO | ESP32 → PC | 设备描述字符串 |
| `0x07` | HELLO_ACK | PC → ESP32 | — |
| `0x08` | AUDIO_STATE | ESP32 → PC | `[1]`=active(0/1)，`[2..5]`=buffered(uint32) |
| `0x09` | EMOTION | PC → ESP32 | `"EMO:HAPPY"` 整行 |
| `0x0A` | INTENT | PC → ESP32 | `"INTENT:CHAT"` 整行 |
| `0x0B` | TD_TEXT | PC → ESP32 | 任意一行，原样转发给 TD1601 |
| `0x0C` | INTENSITY | PC → ESP32 | `"INTENSITY:HIGH"` 整行 |
| `0x0D` | STATE | PC → ESP32 | `[1]`=code(0~215)，见链路 ② |
| `0x0E` | CAM_REQ | PC → ESP32 | `[1]`=请求序号(0~255) |
| `0x0F` | CAM_DONE | ESP32 → PC | `[1]`=0 成功/1 失败，`[2..5]`=总字节数(u32)，`[6]`=请求序号 |

### 两个必须遵守的约定

**1. 握手是单向发起 + 单向应答**

```
ESP32 --HELLO--> PC --HELLO_ACK--> ESP32（收到 ACK 只清标记，不再回 HELLO）
```

任何一端"有问必答"都会变成 `HELLO ↔ HELLO_ACK` 无限回声，把串口带宽吃满。

**2. 推流要按 ESP32 上报的真实水位限速**

`AUDIO_STATE` 每 100 ms 上报一次 `buffered`（uint32，剩余未播字节）。
PC 侧 `voice_server.py` 据此控制推流节奏：

| 水位 | pace |
|---|---|
| < prefill (0.25 s) | 0.5（加把劲） |
| < target (0.35 s) | 0.9（正常） |
| ≥ target | 1.4（等一等） |

硬上限 `play_max_s = 1.2 s`，绝不把 ESP32 缓冲写满。
上报中断超过 0.5 s 就退回"按时间开环推算"。

## 链路 ②：ESP32 → TD1601（仅一根 PB18，单向）

**介质**：ESP32 `UART2` `GPIO14` → TD1601 `PB18/UART3_RXD`，**115200-8N1**。

> ⚠️ PCB 只引出 PB18，`PB19/UART3_TXD` 未连接，所以这条链路**物理上单向**。
> TD1601 侧 `uart_esp.c` 只配置 RX，不发任何数据。

### 正式协议：状态字节帧

```
0xAA  <code>        共 2 字节，不带换行
```

`code ∈ [0, 215]`，编码规则：

```
code = (emo_id × 8 + intent_id) × 3 + intensity_id
```

解码：

```
intensity_id =  code % 3
intent_id    = (code / 3) % 8
emo_id       =  code / 24
```

**为什么压成一个字节**：PC 原本一轮要连发 3 条命令（INTENSITY + EMO + INTENT
≈ 47 字节），TD1601 主循环 10 ms 轮询，UART3 硬件 FIFO 中途溢出，
命令被截断成 `INTENSITY:EMO:SAD` 这种幽灵命令。压成 1 字节后
3 帧变 1 帧、47 字节变 3 字节。

**编码表**（三处必须完全一致：`pc_baozi/td1601.py`、`esp32_baozi/protocol.h`、
`TD1601 src/uart_esp.c` 的 `k_esp_emo_to_td`）：

| emo_id | 名称 | | intent_id | 名称 | | intensity_id | 名称 |
|---|---|---|---|---|---|---|---|
| 0 | neutral | | 0 | none | | 0 | low |
| 1 | happy | | 1 | greeting | | 1 | medium |
| 2 | sad | | 2 | question | | 2 | high |
| 3 | angry | | 3 | chat | | | |
| 4 | surprised | | 4 | command | | | |
| 5 | loving | | 5 | thanks | | | |
| 6 | idle | | 6 | goodbye | | | |
| 7 | bored | | 7 | unknown | | | |
| 8 | sleeping | | | | | | |

> emo 的 **6=idle / 7=bored / 8=sleeping 是"心情"不是"情绪"**。
> 两处最易错：3=angry（不是 surprised）、4=surprised（不是 angry）。

### 兼容协议：文本行

调试时可直接发文本（TD1601 `uart_esp.c` 的状态机会自动识别）：

```
EMO:HAPPY\n
INTENT:CHAT\n
INTENSITY:HIGH\n
TRACK:ON\n     / TRACK:OFF\n      红外跟随开关
```

`0xAA` 是不可打印字符，与任何文本行都不会混淆，两种格式可以混发。

TD1601 侧单行缓冲 **64 字节**，超长整行丢弃并计数 ——
**绝不截断后半段当命令执行**（截断会造出 `INTENSITY:EMO:SAD` 那种幽灵命令）。

## 链路 ③：PC ↔ TD1601（文本帧，独立串口）

**介质**：独立 USB-TTL → TD1601 `UART0` `PA18(TX)/PA17(RX)`，115200-8N1。
（这根线同时是 `printf` 日志口，所以上行是"日志 + 协议帧"混流，
解析时必须扫帧头 `0xA5` + 验校验来过滤。）

### 帧结构

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | `0xA5` |
| 1 | 1 | LEN（DATA 长度，≤255） |
| 2 | 1 | CMD |
| 3 | LEN | DATA |
| 3+LEN | 1 | CHECKSUM = `0xA5 ^ LEN ^ CMD ^ DATA[0] ^ … ^ DATA[n-1]` |

总帧长 ≤ 259（`FRAME_MAX_SIZE`）。

### 下行命令（PC → TD1601）

| CMD | 名称 | DATA 布局 |
|---|---|---|
| `0x01` | SET_EMOTION | `[emotion:1]`（0x00~0x06） |
| `0x02` | SEND_EVENT | `[event:1]` |
| `0x03` | SWITCH_PERSON | `[name_len:1][name:N]` |
| `0x04` | PLAY_SCRIPT | `[name_len:1][name:N]` |
| `0x05` | STOP_SCRIPT | — |
| `0x06` | SET_SERVO | `[servo_id:1][angle:1]` |
| `0x07` | RESET | — |
| `0x08` | QUERY_STATUS | — |
| `0x09` | HEARTBEAT | — |
| `0x0A` | DANCE | — |
| `0x10` | SYNC_TIME | `[mon][day][weekday][hh][mm][ss?]` |
| `0x11` | HABIT_BEGIN | `[count:1]` |
| `0x12` | HABIT_ITEM | 见下 |
| `0x13` | HABIT_END | `[count:1]` |
| `0x14` | SCHED_BEGIN | `[count:1]` |
| `0x15` | SCHED_ITEM | 见下 |
| `0x16` | SCHED_END | `[count:1]` |
| `0x17` | REMIND | 见下 |

### 上行报告（TD1601 → PC）

| RSP | 名称 | DATA |
|---|---|---|
| `0x81` | STATUS | `[emo][energy][idle_h][idle_l][emo_h][emo_l]` |
| `0x82` | SENSOR | `[sensor_type:1]`（0=触摸 1=红外） |
| `0x83` | SCRIPT_DONE | — |
| `0x84` | SERVO_DONE | — |
| `0x90` | HABIT_CHECKIN | `[idx][slot][action]`（0=打卡 1=取消） |
| `0x91` | HABIT_SYNCED | `[count]`（日程同步完成也复用它） |
| `0x92` | HABIT_REQ | —（板子空手，催 PC 重发） |
| `0x93` | SCHED_CHECK | `[idx][action]`（0=完成 1=撤销） |
| `0x94` | SCHED_REQ | —（催 PC 重发日程） |
| `0x95` | REMIND_CLOSED | `[type][reason]`（0=点击 1=超时） |
| `0x8F` | ERROR | `[code:1]` |

### HABIT_ITEM（0x12）DATA 布局 — 16 字节头 + 点阵

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | idx | 序号 0..count-1 |
| 1 | mode | 0=单次 / 1=多次 |
| 2 | total | 格子总数 1..32 |
| 3 | done | 已确认格子数 |
| 4 | state | 0=未来 1=待打卡 2=已完成 3=错过 |
| 5 | cur_slot | 当前可打卡格子；`0xFF`=无 |
| 6..7 | streak | 连续天数（u16 小端） |
| 8..11 | mask | 已完成格子位掩码（u32 小端，bit i = 第 i 格） |
| 12 | name_chars | 名字字数 0..6（0=不画名字） |
| 13 | name_w | 点阵宽（像素，须为 8 的倍数） |
| 14 | name_h | 点阵高（像素） |
| **15** | **open_max** | 已开窗的最大格子序号（含）；`0xFF`=一格都没开 |
| 16.. | bitmap | 逐行扫描，每行 `name_w/8` 字节，MSB = 最左 |

**`open_max` 为什么必须有**：板子只拿得到「总状态 + cur_slot + mask」，
分不出某格是"还没到时间"还是"已错过、可补卡"。一天三次的习惯，13:00 时
前两格 missed、第三格 future，`cur_slot=0xFF`，板子会把第三格也当成能点 ——
用户点一下，未来那次就被提前记上。PC 把"已开窗到第几格"算好发下来，
板子只比大小，不需要懂任何时间规则（判定源仍然只有后端一个）。

**为什么名字用点阵而不是字库索引**：习惯名是用户自己起的中文，
板载字库不可能覆盖。PC 渲染好点阵传下来，任意中文都能显示，也不占 Flash。

长度校验：`len >= 16 + ceil(chars × name_w / 8) × name_h`，否则丢帧回 `ERR_LEN_MISMATCH`。
上限：6 字 × 16×16（32 B）= 192 + 16 = 208 < 255，单帧装得下。

### SCHED_ITEM（0x15）DATA 布局 — 10 字节头 + 点阵

| 偏移 | 字段 |
|---|---|
| 0 | idx |
| 1 | mon（1..12） |
| 2 | day（1..31） |
| 3 | weekday（1=周一 .. 7=周日） |
| 4 | hh |
| 5 | mm |
| 6 | status（0=待办 1=完成） |
| 7 | title_chars（0..6） |
| 8 | title_w（像素，8 的倍数） |
| 9 | title_h（像素） |
| 10.. | bitmap |

上限：`10 + 6 × (16/8) × 16 = 202` < 255。
下发顺序按 `(date, time)` 升序，只发"今天及以后"，最多 12 条。

### REMIND（0x17）DATA 布局 — 6 字节头 + 点阵

| 偏移 | 字段 |
|---|---|
| 0 | type（0=习惯 1=日程） |
| 1 | hh |
| 2 | mm |
| 3 | title_chars（0..7） |
| 4 | title_w |
| 5 | title_h |
| 6.. | bitmap |

上限：`6 + 7 × (16/8) × 16 = 230` < 255。

**谁判定时机**：**只有 PC**（轮询后端：习惯 slot 变 pending、日程开始前 10 分钟）。
板子不存时间表、不做任何判定，收到 0x17 就弹卡。声音也从 PC 出（板子无喇叭）：
PC 用 EdgeTTS 先播，再发 0x17。

### 交互闭环

```
PC 桥接脚本                                  TD1601
  ── 0x10 对时 ──────────────────────────►   更新顶部时钟
  ── 0x11 HABIT_BEGIN ───────────────────►   清空旧缓存
  ── 0x12 HABIT_ITEM ×N ─────────────────►   逐个写入
  ── 0x13 HABIT_END ─────────────────────►   重绘卡片 + 回 0x91
  ◄──────────── 0x92 REQ ─────────────────   板子空手，催 PC 重发
  ◄──────────── 0x90 CHECKIN ─────────────   用户点了某格
  ◄──────────── 0x93 SCHED_CHECK ─────────   用户点了日程行
  ◄──────────── 0x95 REMIND_CLOSED ───────   弹卡被关闭
```

`0x92` 存在的意义：板子可能比 PC 先开机，这时屏幕是空的。没有它，
实机上表现为「屏幕显示 waiting data...，点什么都没反应」，看起来像坏了。

### 错误码

| 码 | 含义 |
|---|---|
| `0x01` | 未知命令字 |
| `0x02` | 数据长度错误 |
| `0x03` | 校验失败 |
| `0x04` | 情绪编号越界 |
| `0x05` | 性格包未找到 |
| `0x06` | 脚本未找到 |
| `0x07` | 习惯序号越界 / 点阵长度不足 |
| `0x08` | 习惯缓存已满 |

### 设备端容量上限（PC 下发前对照）

| 项 | 值 |
|---|---|
| `HABIT_MAX_COUNT` | 12 |
| `HABIT_MAX_SLOT` | 32 |
| `HABIT_NAME_MAX_CHARS` | 6 |
| `SCHED_MAX_ITEMS` | 12 |
| `SCHED_TITLE_MAX_CHARS` | 6 |
| `REMIND_TITLE_MAX_CHARS` | 7 |

⚠️ 改这些值必须同步 `pc_baozi/app/board.py` 与 TD1601 的 `include/uart_protocol.h`，
否则握手校验对不上、超出的条目会被静默截断。

## 协议一致性核对方法

三套协议都有「同一份定义、多处实现」的问题。核对方式：

```bash
# 链路 ① 控制码：Python 枚举 vs C 宏
grep -oE "^    [A-Z_]+ = 0x[0-9A-F]+" pc_baozi/protocol.py
grep -oE "#define CTRL_[A-Z_]+ +0x[0-9A-F]+" esp32_baozi/protocol.h

# 链路 ③ 命令集：Python 表 vs C 枚举
grep -nE "\"(emo|habit_begin|remind)\":" pc_baozi/app/board.py
grep -oE "CMD_[A-Z_]+ *= *0x[0-9A-F]+" <TD1601>/include/uart_protocol.h
```

2026-10-28 核对结果：链路 ① 的 15 个 `CTRL_*` 两侧一一对应；
链路 ③ 的 18 个下行、11 个上行 PC 侧全部覆盖；
两版 `uart_protocol.h` / `baozi_hooks.h` 逐字节相同。
